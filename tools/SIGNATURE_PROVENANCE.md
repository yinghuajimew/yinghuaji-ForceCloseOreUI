本文记录 `SIG_FALLBACK`（独立版）与 `OREUI_PATTERN`（依赖版）里每一条特征的**来源、
引入时间、是否经过实测**，以及已知的失效项。

目的很简单：这张表是多年累积下来的，里面既有实测过的，也有「先放进去看看」的。
不记下来，下一次谁也不敢删。

## 四、两个版本各自的问题

### 依赖版：JNI 钩子签名失效（`Hook1`）

`b8887db` 记录：`Hook1` 所用的签名在**全部 6 个样本上零命中**，当前版本上不会生效。

保留原样是因为它参与 `pl::hook` 的静态注册器结构，删掉会破坏编译。
**如果某版本上 `Hook1` 没生效，先怀疑这里，不要先怀疑 `OREUI_PATTERN`。**

### 独立版：没有对应问题

独立版不使用 `SKY_AUTO_STATIC_HOOK`，没有这个失效项。

## 五、1.20 不能直接复用 1.26 的钩子目标

这条容易踩，单独记：

`H2` 在 1.20.10.01 上命中 `0x56DBB0C`，**是函数入口**。但该函数引用的字符串是：

```
/gameplay/death   /hbui/gameplay.html   JsException   ScreenLoadFailed
core:routing:not-found   core:gui:resize-hack   core:exception
core:telemetry:firstContentfulPaint   core:telemetry:firstMeaningfulPaint
core:keyboard:dismissed   Play   Edit World
```

全是 **HBUI/OreUI 运行时核心**（路由表、异常、遥测、键盘）。

而 1.26.62.1 的目标函数引用的是 `/oreui-marketplace/search`、`/send-invites`
这类**具体界面路由**。

两者不是同一个函数。所以：

| 版本 | 状态 |
|---|---|
| 1.20.10.01 | 运行时核心已存在，界面仍以 JSON-UI 为主 |
| 1.21.x | OreUI 界面逐个出现 |
| 1.26.x | 几乎所有界面都是 OreUI |

**「去 OreUI」不是开关，是逐版本、逐界面的事。**

## 六、命中 ≠ 可用

`DobbyHook` / `pl::hook` 在函数中间下钩子，会覆盖被调用的指令或破坏栈帧，
行为不可预期。

| 版本 | 命中地址 | 前一条指令 | 是函数入口 |
|---|---|---|---|
| 1.20.10.01 | `0x56DBB0C` | `ret` | ✅ |
| 1.21.0.03 | `0x5F85100` | `ret` | ✅ |
| 1.21.90.3 | `0x5EC9928` | `ret` | ✅ |
| 1.21.132.1 | `0x907E4BC` | `bl` | ❌ 真实函数头在 `0x907E3D4` |
| 1.26.0.2 | `0x913DF54` | `bl` | ❌ |
| 1.26.62.1 | `0x9AF937C` | `ret` | ✅ |

**所以在 1.21.132.1 和 1.26.0.2 上，现有特征码的钩子很可能是坏的**，
不是「能跑但效果不好」。

## 七、如何为新版本补特征码

不要手写，不要猜。用 `tools/derive_sig.py`：

```bash
python3 tools/derive_sig.py libminecraftpe.so
```

或者在 GitHub Actions 上跑（见 `tools/README.md`），无需本地环境。

推导完成后**务必**用 `scan.py` 回验命中处是否落在函数入口：

```bash
python3 tools/scan.py libminecraftpe.so
```

`derive_sig.py` 已内置自验（`609203b` 加入），会直接报告是否落在函数入口。

## 八、维护约定

1. **新增特征码必须附实测版本号与命中地址**，否则下一个维护者无法判断可信度。
2. **未实测的模式不要标注版本区间**。`H5` 就是因为标注了不存在的关系而误导。
3. **实测零命中的条目要写进「已丢弃」并留下理由**，不要只删掉了事。
4. 固定特征码表**必然随版本腐化**，长期方案是每次新版本用工具重推。
